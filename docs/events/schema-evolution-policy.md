# Schema Evolution Policy & Compatibility Rules (LAB-901)

## 1. Schema Compatibility Principles

In an event-driven architecture, event producers and consumers deploy independently. To prevent producers from breaking downstream systems, all domain events published to the message backbone must strictly adhere to the following schema evolution rules.

### Compatibility Definitions

1. **Backward Compatibility**:
   - Newer code can read data generated by older code.
   - Example: A consumer running with **v2** schema can safely read and process **v1** events produced by legacy instances.
2. **Forward Compatibility**:
   - Older code can read data generated by newer code.
   - Example: A consumer running with **v1** schema can safely read **v2** events (ignoring newly added fields without crashing).
3. **Full Compatibility**:
   - Both backward and forward compatibility are maintained simultaneously.

---

## 2. Allowed vs. Forbidden Schema Changes

### ✅ Allowed (Non-Breaking) Modifications
- **Adding Optional Fields**: New fields must be optional or have sane default values.
- **Publishing New Event Types**: Adding a new event (e.g. `order.compensated`) does not impact existing consumers who only listen to `order.confirmed`.
- **Enriching Metadata**: Adding tracing headers (`correlationId`, `causationId`) inside the optional `metadata` block.

### ❌ Forbidden (Breaking) Modifications
- **Removing Existing Fields**: A consumer relying on `orderId` or `totalAmountCents` will break if the field disappears.
- **Renaming Fields**: Renaming `totalAmountCents` to `priceInCents` is a breaking change.
- **Changing Data Types**: Changing `quantity` from an integer `2` to a string `"2"`.
- **Changing Meaning / Semantics**: Changing `confirmedAt` from UTC ISO timestamp to epoch milliseconds.

---

## 3. The Upcasting Pattern (Schema Migration)

When a consumer requires a newer version (e.g. v2) but reads older historical events from the log (e.g. v1), Launchpad uses **In-Memory Upcasting** via `EventSerializer.upcast(...)`:
- The raw byte representation on disk/topic remains unchanged (preserving immutable event logs).
- The deserializer applies an explicit transformer function `v1 -> v2`:
  ```typescript
  EventSerializer.registerUpcaster('order.confirmed', 1, 2, (v1Data) => ({
    ...v1Data,
    customerEmail: (v1Data as any).customerEmail || 'no-reply@launchpad.internal',
    ticketTierName: 'General Admission',
  }));
  ```

## 4. Review Questions Answered

### Question 1: What data is too much? Too little?
- **Too Little (Thin Notification / Event-Notification)**:
  - Example: Emitting `{ "orderId": "123" }` and nothing else.
  - *Failure Mode*: Every consumer (email service, analytics, billing, fraud) receives the event and immediately queries the producer's PostgreSQL database (`GET /api/orders/123`). This results in a massive **stampede (N+1 query storm)** on the primary transactional database, completely defeating the purpose of asynchronous scale!
- **Too Much (Overly Fat / Leaky Payload)**:
  - Example: Dumping the entire internal PostgreSQL database row, internal password hashes, raw gateway credentials, or internal concurrency locks.
  - *Failure Mode*: Violates encapsulation, leaks database schema internals, breaches compliance/GDPR privacy rules, and bloats message broker memory.
- **The Golden Rule (Event-Carried State Transfer)**:
  - Include the **minimal, stable facts** required for 80-90% of downstream business consumers to execute their tasks without making callbacks to the producer database.

### Question 2: Who owns the schema?
- **The Producer Owns the Schema**:
  The emitting domain boundary (`OrderService`) is the authoritative owner of the domain event contract. It defines the business semantics and guarantees that the facts emitted are true statements about its domain model.
- **Consumers Provide Consumer-Driven Contract Tests (Pact / CDC)**:
  While the producer owns the schema, consumers publish expectations (contract tests). Before a producer ships a new schema version, CI verifies that all active consumer contracts remain fulfilled.
